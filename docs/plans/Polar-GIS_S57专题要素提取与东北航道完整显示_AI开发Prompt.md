## 一、角色、目标和基本原则

你是一名熟悉 IHO S-57、GDAL/OGR、PostGIS、FastAPI、Vue 3、TypeScript、OpenLayers、GeoServer 的 GIS 全栈开发工程师。请对真实项目代码进行修改，不只给出概念方案、伪代码或演示数据。

需要完成两组任务：

1. **在现有航道专题提取/保存的基础上，新增完整 S-57 海图的其他专题要素提取和独立文件保存功能**，优先包括水深、障碍物、沉船、水下礁石，尽量复用现有项目/数据集/版本、PostGIS 数据和快照导出体系；为后续航线规划的水深约束、障碍物规避保留原始信息。
2. **修复与完善航道图层的完整显示和信息交互**。检查是否因为导入范围、项目关联、对象类选择、200 个图层上限、2,000 条预览上限、服务端过滤、地图比例尺/样式或前端状态造成不完整显示；增加可理解的航道信息查看、显示数量和覆盖范围说明，并对东北航道进行权威地理资料对照。

约束：

- 不破坏海图批量导入、GeoServer/GWC/WMTS/WMS、智能图层调度、冰情时间轴、底图恢复、测距、航路手绘、航线规划和现有航道快照 API。
- 不改用新的前端地图引擎；不引入独立 GIS 服务、消息队列或全新微服务；尽量不增加数据库表/迁移。优先沿用 `backend/app/services/`、`backend/app/api/`、前端现有 composable 和面板。
- 不把交通分隔制边界、深水区域或断续要素拼接成所谓“官方东北航道”；不生成虚构坐标、虚构水深或不存在的航行路线。
- **优先实现功能，其次做最少且必要的验证**。不开展几百条新自动化用例、长时间压力测试、复杂基准平台或大规模架构重构。
- 不随意更改现有数据，也不覆盖旧导出成果；已有变更和用户本地文件必须保留。

### 2.2 当前代码中的现成能力和疑点

已发现并须优先复用：

- `backend/app/services/s57_layer_catalog.py`：S-57 图层分类事实来源，已有 `DEPARE`、`DEPCNT`、`SOUNDG`、`OBSTRN`、`WRECKS`、`UWTROC` 等类别。
- `backend/app/services/s57_waterway_catalog.py`：航道专题分类，区分主要航道/推荐航路与辅助要素；请不要把 `DEPARE/DEPCNT/SOUNDG` 直接重新算作航道。
- `backend/app/services/s57_waterways.py`：按项目关联、当前数据集版本、available/queryable 等条件检索 `geo.*` 表。`resolve_waterway_layers()` 在收集候选层后执行 `candidates[:settings.s57_waterway_max_layers]`，默认 **200 层**，可能在后续筛选前遗漏重要层。
- `backend/app/services/s57_waterway_export.py`：已有航道快照 `waterways.geojson` + `manifest.json`、键集分页、原子写入、来源版本/哈希、`stale` 标志。`preview_waterway_items()` 默认最多 **2,000 条**，`create_waterway_snapshot()` 默认最多 **20,000 条**；`_extract_features()` 当达到阈值时直接将 `truncated=True`，需核实是否真正存在下一条数据，避免刚好达到阈值时误报。
- `backend/app/api/s57_waterways.py`：已有 `catalog/search/preview/snapshots/{id}/download` 等项目级接口；`backend/app/api/layers.py` 另有单图层 `/exports`，但有普通导出限额。
- `frontend/src/composables/useS57Waterways.ts`：`showOverview()` 对选中类别发起单次 preview，覆写现有 `displayed` 并调用 `map.getView().fit()`；尚不支持分区域增量加载大量航道要素。
- `frontend/src/components/S57WaterwayPanel.vue`：**已存在“航道要素详情”抽屉**，包括名称、类别、来源、几何范围、S-57 原始属性。此次应补强易用性与地图联动，而非再造重复抽屉。
- `frontend/src/utils/mapS57Waterway.ts`：独立矢量叠加、分组颜色，橙色表示交通分隔制等对象；必须保持与手绘航线/智能规划结果隔离。
- `backend/app/services/importer.py`：当前 `ogr2ogr` 批量导入命令含 `-nlt PROMOTE_TO_MULTI`，未显式设置 `-oo SPLIT_MULTIPOINT` / `-oo ADD_SOUNDG_DEPTH`。需确认 SOUNDG 真实的 3D/Z 深度是否被完整保留、PostGIS 类型是否适合按点提取，**先诊断再决定是否添加针对性读取逻辑，不要贸然改变所有 ENC 导入行为**。

### 2.3 对“东北航道”的正确理解

- 东北航道 Northeast Passage（NEP）和俄罗斯北方海航道 Northern Sea Route（NSR）是相关但不完全同一的地理/管理概念，应在页面、诊断报告和代码中明确名称。
- 权威资料可参考北极理事会 PAME 的 *Arctic Marine Shipping Assessment*、美国国家冰情中心 USNIC 的 *Arctic Sea Routes*、Arctic Portal / Northern Sea Route Information Office 的路线图。
- USNIC 的 NSR 冰情/海路图产品覆盖区域约为 **70°N 以北、40°E 至 160°W**；这是该图产品的覆盖范围，**不是官方法定航道边界或唯一推荐航线**。不要把上述范围硬编码为每条航道要素必须落入的唯一规则，只可作为排查用的宽松区域参考。
- S-57 ENC 的水深区域、海图符号、交通分隔制和推荐航行线都是**局部航海信息对象**，并不能保证天然形成一条从欧洲到白令海峡的连续 LineString。若没有足够海图单元或权威路线几何，应如实显示“覆盖不全”，不得自动补线后冒称 S-57 官方航道。

## 三、任务 A：新增水深、障碍物等 S-57 专题的独立提取与保存

### A1. 先建立真实提取范围和对象分类

1. 从项目已关联、当前有效版本的 S-57 图层/`geo.*` 表中发现实际存在的对象类；可复用 `s57_layer_catalog.py` 的名称/分类，但**不要仅靠静态枚举表判定完整性**。
2. 增加可扩展的“专题数据提取类别”配置，首批支持下表；其他确实导入的空间对象类允许用户按类选择导出，不强制一次实现全部对象的复杂业务解释。

| 专题 | 首批 S-57 对象类 | 核心保留内容 |
|---|---|---|
| 水深与海底地形 | `SOUNDG`、`DEPCNT`、`DEPARE` | 真实点/线/面几何、Z/深度值、`VALDCO`、`DRVAL1/2`、垂直基准及质量字段 |
| 水深相关补充 | `DRGARE`、`SWPARE`、`UNSARE`、`M_QUAL` | 疏浚/扫测/未测区及质量信息；应按各自对象语义展示，不视为可靠实测水深 |
| 危险物 | `OBSTRN`、`WRECKS`、`UWTROC` | 障碍物、沉船、礁石的真实几何、`VALSOU`、`WATLEV`、`CATOBS/CATWRK`、`EXPSOU`、`QUASOU` 等可用属性 |
| 航道与相关信息 | 复用当前航道分类，进一步按 IHO 目录核对 `DWRTCL`、`DWRTPT`、`RCRTCL` 等可能漏掉的对象 | 不改变原航道快照格式，若确有编码遗漏再补充分类及中文解释 |

**关键数据语义要求：**

- `SOUNDG` 可能是具有 Z 值的 MultiPoint；每个测深点的深度可能在几何第三维而不是普通属性列。检验 `ogrinfo` 的点位和 PostGIS 中的 `ST_Z`、`ST_NDims`、`ST_DumpPoints`；不能把深度当作经纬度坐标或用 `DEPARE` 范围替代测深值。
- 先判断现有 `SOUNDG` 是否已保留 Z。若有，直接从现有表提取；如确实丢失，再为 SOUNDG 增加**独立可控的精准提取通路**，参考 GDAL S57 驱动的 `SPLIT_MULTIPOINT=ON` 与 `ADD_SOUNDG_DEPTH=ON`，注意后者依赖前者。不要无条件重导入全量海图。
- `DEPARE.DRVAL1/DRVAL2` 表示区域水深范围，`DEPCNT.VALDCO` 表示等深线数值，危险物的 `VALSOU` 是其测深相关属性；这些都**不等价于航道保证水深或船舶可安全通行深度**。保留 `VERDAT`、`M_QUAL/CATZOC` 等质量/基准信息，缺失时标为“未知”。
- 坚持真实几何与属性：不插值生成不存在的深度点、不计算虚假障碍物位置、不硬造水深安全判断；保留原始枚举代码，只有在找到权威 IHO 字典时才展示中文枚举解释。
- 支持 WGS84 `EPSG:4326` GeoJSON 导出；经纬度为 `[lon,lat]`。如果深度通过独立字段存储，明确该字段来源、单位、符号和基准，且同时保留原始 `Z` 或其他源字段，不擅自取绝对值/改正负号。避免意外把 3D GeoJSON 降为 2D。

### A2. 提取范围与过滤功能

最小可用界面支持：

1. 选择提取专题（水深、危险物、航道/其他）和具体对象类（多选）。
2. 选择来源：当前项目中已关联的 S-57 数据集/图层，或在已有授权范围内指定某个数据集/海图 Cell；首版不要求跨权限导出全服务器数据。
3. 选择空间范围：默认“当前项目的全部有效数据”；可选“当前视口范围”；明确标注当前筛选条件，不要把当前地图缩放范围默认当成全部数据。
4. 展示预计数量：总源图层数、可提取层数、源要素数量及不可提取原因；数量未知要明确标注。
5. 点击“提取并保存”后，服务端分批提取**全部符合筛选条件的真实要素**，而不是只保存当前搜索页或前 2,000 条预览数据。

对于 `SOUNDG` 等海量数据，避免把所有记录一次性读进 Python 内存。沿用现有键集分页思路，优先 **500～2,000 条/批**，以流式方式写 GeoJSON；对一个 S-57 对象类由多个 Cell 组成的情况，也要逐 Cell/逐层推进。

### A3. 独立文件、成果目录和溯源

优先仿照 `s57_waterway_export.py` 的原子写入与成果元数据模式，建议服务模块为 `backend/app/services/s57_thematic_export.py`，路径仅为建议，开发时以实际项目命名为准。

推荐文件布局（每个成果独立保存，不覆盖历史快照）：

```text
<STORAGE_ROOT>/navigation/s57-thematics/<projectId>/<exportId>/
  manifest.json
  depth/
    SOUNDG.geojson
    DEPARE.geojson
    DEPCNT.geojson
  hazards/
    OBSTRN.geojson
    WRECKS.geojson
    UWTROC.geojson
  other/
    <实际选中的对象类>.geojson
```

- 按选择的对象类输出，未选择或不存在的对象不必创建空文件；如文件过大，可采用按 Cell 或分卷策略，并在 manifest 中列出全部分卷，**保证可完整恢复记录集合**。
- 文件采用标准 GeoJSON `FeatureCollection`；各 feature 携带真实 `geometry` 和 `properties`。至少保留：`objectClass`、原始属性 `originalAttributes`、`sourceCell`、`sourceLayerId`、`sourceDatasetId`、`sourceVersionId`、`sourceVersionNo`、可用的原始标识 `LNAM/RCID/FIDN/FIDS/ogc_fid`、`geometryType`、与深度有关的字段或 metadata。
- 输出 `manifest.json`，包含 `schemaVersion`、项目/成果 ID、创建时间、类别与条件、范围 bbox、坐标系、各对象类与各 Cell 数量、文件列表、数据集/版本/原始哈希、文件 SHA256、警告、是否完整 `complete`/是否截断 `truncated`、失败及跳过原因。
- 原子写：临时目录写入成功后移动至正式目录；错误时清理自身临时文件，不留下看似成功的残缺成果。
- 不依赖临时浏览器 Blob 保留成果；使用现有后端共享持久化存储卷，重启后仍可列出与下载。
- 若范围过大而触发安全阈值，必须**清楚提示并阻止将不完整文件标记为完整**；优先支持分卷完整导出，受限时明确返回 `partial/truncated`，并允许用户按 Cell/对象类缩小范围。不要只是把配置从 20,000 改成无限大。
- 下载可使用单个 GeoJSON；多文件时提供 ZIP 下载入口（若实现 ZIP 简单则做；否则分别下载并保留清单），不要新增对象存储服务。
- 将成果严格定位为“航线规划的原始候选数据”，不是经过安全论证的通航网络。后续规划算法需要自行判断船舶吃水、潮汐基准、冰况、数据质量和航行限制。

## 四、任务 B：航道显示片段化的逐级诊断与修复

### B1. 先以证据区分数据不完整与程序不完整

做一次**低成本、可重复**的航道完整性核查，生成一张对照表，分别统计：

1. **源文件级**：实际导入目录中存在的 `.000` 基础 Cell、对应 `.001/.002/...` 更新文件和版本号；S-57 `DSID`、`M_COVR` 或 `ogrinfo -ro -so -al -json` 能得到的对象类、数量、覆盖范围。应区分没有文件、更新链间断和读取失败。无需全量重跑导入。
2. **数据库级**：与源 Cell 对应的 Dataset、当前 DatasetVersion、`geo.*` 实际表/真实 `COUNT(*)`/几何类型/`ST_Extent`，是否存在空间对象但未正常发布；区分仅 GeoServer 不可渲染与 PostGIS 仍可检索。
3. **项目关联级**：`ProjectLayer` 中是否关联该 Cell 的航道层；仅关联了核心海图/概览底图却未关联全部专题图层时，要给出明确说明。
4. **分类/筛选级**：对象类是否被当前 `s57_waterway_catalog.py` 覆盖，是否 `available/queryable`，是否辅助层、未被勾选、被 keyword/bbox/版本条件过滤；若某对象类未纳入航道目录，参照 IHO 核实后再修订。
5. **查询/预览级**：目录候选数、200 层截取数、每类匹配数、实际返回数、2,000 条显示限制、是否存在当前视口 bbox、网络失败/超时及 `truncated` 标志。
6. **前端渲染级**：`displayed`、VectorSource、geometry 数、渲染可见性、投影变换和 `fit()` 范围；单要素/整体 bbox 与当前视图匹配情况；必要时检查 WMS 比例尺样式、zIndex、图层显隐及 GeoServer 有无隐藏非当前比例尺要素。

诊断结果按 Cell/对象类汇总成适合 UI 展示的简单数据结构，至少能指出“源文件不存在 / 未导入 / 未关联项目 / 无对应对象 / 被过滤 / 超上限 / 未成功显示”的具体原因。不要把所有结果笼统写成“航道加载失败”。

可增加只读 `GET /api/v1/projects/{projectId}/s57-waterways/diagnostics`（或在现有 catalog 中扩展统计）。返回**数量、分组、Cell 与地理覆盖范围**，不要向普通用户暴露任意 SQL、数据库连接串或内部凭据。

### B2. 修复有确凿证据的数量与显示限制

1. 检查 `resolve_waterway_layers()` 中默认 200 层候选先截断的问题。优先按可用性、数据集/Cell、对象类顺序稳定遍历**所有有效候选**，按批次处理，而不是静默只取前 200 个。若需设置每批查询预算，应把“单批最大数”与“可遍历全部图层”区分开。
2. 现有 `/preview` 默认上限 2,000 条不可简单无上限放开。实现**按视口/Cell/对象类分页或分批增量查询和显示**；数据规模大时以视口查询和性能预算控制前端，只保留当前范围所需数据。显示层应与现有 S-57 Render Bundle 和手绘航路保持隔离。
3. 返回 `matchedTotal`（真实匹配总数或明确标记未计算）、`returnedCount`、`displayedCount`、`hasMore`/`nextCursor` 或等效分页状态。让用户知道到底是“仅显示前 N 条”还是“整个项目本来只有 N 条”。
4. 不把“本次请求恰好返回 max_features 条”直接认定为确实截断。可通过额外读取一条来确认 `hasMore`，或给出有证据的完整性状态。
5. `showOverview()` 当前用全新 Map 覆盖旧结果，追加下一批时需要按稳定 feature ID 去重并增量合并；区域切换、投影切换、卸载必须取消过期请求、清理旧叠加。防止“批次 2 返回后把批次 1 覆盖掉”。
6. 对地图缩放过低造成的橙色碎片化视觉效果：仍按真实几何类型绘制线、面，优化不同 zoom 的线宽/填充透明度/符号大小与图例提示；对于 `TSSLPT/TSEZNE` 面状交通分隔区，**不要通过线化/连接两个不相关面片将其变成通航路线**。低缩放下可显示类别概览或提示“放大以查看详细要素”。
7. 前端允许“只看航道/推荐航路”和“显示交通分隔制/辅助要素”的独立开关，避免大量橙色交通管制图案让用户误以为是完整航行线路。
8. 默认不限制“仅当前视口”的全部区域检索，但**实际浏览器渲染要受合理预算控制**，后台总量与前端载入数分开展示。检查高纬度和 180° 经线跨越情形，确保查询 bbox 拆分与投影显示正确。

### B3. 增强真正可用的“具体航道信息查看”

现有 `S57WaterwayPanel.vue` 已有详情抽屉，不必重复从零写。需要实现以下用户可感知改进：

- 在已显示的航道、推荐航路、交通分隔制对象上**点击或通过列表选中**，触发高亮，显示简洁浮窗（对象名称/类别、源 ENC Cell、来源数据集、几何类型、关键属性），并可“查看完整详情”。
- 完整详情扩展：`OBJNAM/NOBJNM`、`INFORM/NINFOM`、对象类中英文、原始对象标识 `LNAM/RCID`、所属 Cell、数据版本、更新日期、原始属性表、几何范围、可获取的类别/管制字段。字段空值写“未提供”，不得虚构名称、维护状态、方向或保证水深。

- 面板顶部增加紧凑统计：“当前项目已关联 X 个 ENC Cell / 可检索航道 X 层 / 实际匹配 X 条 / 地图已显示 X 条 / 未显示 X 条 / 数据覆盖说明”，数量无法精确统计时显示“未知”并给出原因。
- 地图图例需明确“交通分隔制 ≠ 推荐航路；局部 S-57 要素 ≠ 完整规划航线”。新抽屉和已有图层内联图例、航道快照入口均保留。
